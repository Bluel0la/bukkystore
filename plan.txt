## Aunt’s Fashion Store — Reference Project Plan  
## 1. Project Goal  
Build a lightweight, mobile-first e-commerce platform for a small fashion business selling:  
* Clothing  
* Shoes  
* Bags  
* Fashion accessories  
The system should prioritize two things:  
**For customers:** discovering and buying products should take as few steps as possible.  
**For your aunt:** adding products, changing stock, checking orders and viewing performance should require almost no technical knowledge.  
The platform is therefore closer to:  
**Instagram/TikTok-powered digital storefront + inventory + payments + analytics**  
than a complex traditional e-commerce platform.  
  
⸻  
  
## 2. Core Business Assumptions  
These are our current project assumptions.  

| Area               | Decision                                    |
| ------------------ | ------------------------------------------- |
| Business type      | Small fashion retailer                      |
| Products           | Clothes, shoes, bags, accessories           |
| Inventory          | Multiple units per product                  |
| Product variations | Sizes, colours, shoe sizes where applicable |
| Delivery           | Within one city                             |
| Payment            | OPay initially                              |
| Customer accounts  | Not required                                |
| Checkout           | Guest checkout                              |
| Customer support   | WhatsApp                                    |
| Marketing channels | TikTok, Instagram, WhatsApp                 |
| Main admin user    | Your aunt                                   |
| Admin UX priority  | Extremely simple                            |
| Primary device     | Mobile-first, including admin               |
| Architecture       | Modular monolith                            |
  
This prevents unnecessary complexity.

## 9. Inventory Management  
Inventory should operate at variant level.  
Suppose she has:  
```
Brown Linen Set

S    3
M    7
L    4
XL   2

```
A customer buys:  
```
M × 2

```
After successful payment:  
```
M = 5

```
Automatically.  
When:  
```
quantity = 0

```
that specific variant becomes unavailable.  
For example:  
```
Size

[S] [M] [L] [XL]

         ↑
       disabled

```
if L is sold out.  
The entire product only displays:  
Sold Out  
when **every variant has no stock**.  
  
⸻  
  
## 10. Important Inventory Rule  
We should **not reduce stock when somebody merely adds something to their cart.**  
Otherwise abandoned carts could make real inventory appear unavailable.  
The safe early implementation is:  
```
Product added to cart
         ↓
No inventory change

Checkout begins
         ↓
No permanent inventory change

Payment succeeds
         ↓
Verify transaction
         ↓
Reduce inventory

```
Later, if order volume becomes high enough, we can implement temporary stock reservation during checkout.  
For this store, that’s unnecessary initially.

## 18. Cart  
Cart state can initially exist primarily client-side.  
For example:  
```
{
    "items": [
        {
            "variant_id": "...",
            "quantity": 2
        }
    ]
}

```
The frontend sends those IDs when checkout begins.  
However:  
**The frontend must never decide the final price.**  
Suppose somebody manipulates:  
```
₦25,000

```
into:  
```
₦200

```
using browser dev tools.  
Our backend ignores the submitted price.  
It retrieves:  
```
variant
    ↓
product
    ↓
database price

```
and calculates the total itself.  
Important rule:  
**The backend is the authority for price, stock and payment amount.**

## 22. OPay Payment Architecture  
For our initial integration I would favour OPay’s hosted/checkout approach rather than collecting card information ourselves.  
OPay currently documents both pre-built checkout approaches and direct server APIs. Their server-side APIs also expose payment creation, transaction status and payment notifications.   
That’s ideal because we don’t want:  
```
Card number
CVV
Expiry

```
ever flowing through our own application unless there is a compelling reason.  
  
⸻

Our flow should look like:  
```
Customer
   │
   ▼

   ▼

   │

## 24. OPay Webhook  
OPay supports payment notification callbacks. Their documentation describes configuring a callback endpoint that receives transaction-status notifications from OPay.   
So we’d expose something like:  
```
POST /api/v1/payments/opay/webhook

```
Flow:  
```
OPay
 │
 │ Payment status changed
 ▼
Webhook
 │
 ▼
FastAPI
 │
 ├── validate callback
 ├── find transaction
 ├── check reference
 ├── verify payment
 ├── ensure amount matches
 └── update order

```
Then:  
```
PENDING
    ↓
PAID

```
Only then do we:  
```
Reduce stock
Record sale
Record analytics

```
  
⸻  
  
## 25. Payment Verification  
We should have both:  
```
Webhook verification

```
and:  
```
Payment status query

```
OPay’s documentation exposes payment-status APIs specifically for transaction verification.   
So even if:  
```
Webhook fails

```
we can query OPay directly using the transaction reference.  
  
⸻  
  
## 26. OPay Security  
OPay currently uses API-key based authentication and distinguishes secret/public credentials depending on API operation. Their documentation explicitly warns against committing secret keys to Git or placing them in client-side code.   
Our environment therefore contains:  
```
OPAY_MERCHANT_ID
OPAY_PUBLIC_KEY
OPAY_SECRET_KEY

```
Only FastAPI knows them.  
Never:  
```
Next.js client bundle
localStorage
GitHub
frontend .env exposed variables

```
  
⸻  
  
## 27. Order State Machine  
Orders should not merely have:  
```

```

Initially:  
```

        ▼

        │
        ▼

        │
        ▼

```

So:

```

## 33. Why Events Instead of Counters?  
Suppose we only store:  
```

```
We know nothing else.  
With events we can answer:  
```
When?
From where?
Which campaign?
Did they purchase afterward?

```
So:  
```
TikTok
   ↓
Product View
   ↓
Add to Cart
   ↓
Checkout
   ↓
Purchase

```
can belong to one anonymous:  
```
session_id

```
No login needed.

## 43. Checkout Endpoint  
One thing I’d probably do differently from simplistic designs is make:  
```
POST /checkout

```
the central transaction coordinator.  
Request:  
```
{
  "customer": {},
  "delivery_area_id": "...",
  "items": []
}

```
Backend performs:  
```
Validate products

Validate variants

Check stock

Fetch prices

Calculate subtotal

Calculate delivery fee

Calculate total

Create pending order

Initialize payment

```
Then returns:  
```
{
  "order_number": "...",
  "payment_url": "..."
}

```
This keeps checkout consistent.

## 63. Payment Idempotency  
This is one detail I want included from the beginning.  
OPay might theoretically notify us more than once.  
Our backend must safely handle:  
```
Webhook #1
Payment Success

```
and:  
```
Webhook #2
Payment Success

```
without doing:  
```
stock -1
stock -1

```
twice.  
So payment processing must be **idempotent**.  
Something like:  
```
if payment.status == SUCCESS:
    return existing result

```
before any stock mutation.  
Important.  
  
⸻  
  
## 64. Inventory Transaction Safety  
The eventual transaction should essentially do:  
```
BEGIN

verify payment

lock relevant variants

check stock

decrease stock

mark payment success

mark order paid

COMMIT

```
If something fails:  
```
ROLLBACK

```
This prevents corrupt inventory.  
  
⸻  
  
## 65. Analytics Should Never Break Purchasing  
Another architecture rule:  
Suppose analytics fails.  
Checkout should still succeed.  
So:  
```
analytics = useful
commerce = critical

```
We should never create a design where:  
```
Analytics database error
        ↓
Payment fails

```
No.  
If tracking fails:  
```
log failure
continue checkout

```
  
⸻  
  
## 66. Important Product Principles  
I would keep these six rules pinned throughout development:  
**1. Mobile first**  
Most customers will arrive from social media on phones.  
**2. Guest first**  
Do not force registration.  
**3. Social first**  
Every product should be easy to share.  
**4. Aunt first**  
If your aunt finds an admin feature confusing, it’s badly designed.  
**5. Backend authoritative**  
Price, stock and payment state come from the server.  
**6. Start small**  
A reliable simple shop is better than a half-built Shopify clone.

## The next technical step  
I would now move directly into the **database and domain design** before touching frontend code. That’s where we should resolve things like product versus variant, clothing versus shoes, stock behaviour, order snapshots, delivery zones, payment records and analytics sessions.  
From there, we can produce an actual ER diagram and SQLAlchemy models, followed by the FastAPI endpoint contract. That would give us our **engineering blueprint** rather than just the product plan. 🚀  
For OPay specifically, we’ll build against their documented API authentication, transaction-status and callback mechanisms and test in their staging environment before switching credentials/endpoints for production.
